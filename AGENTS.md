# AGENTS.md — guidance for AI agents and human contributors

This file is read by autonomous coding agents and by people. It states how to
contribute to **control-mcp** safely. Read it fully before opening a pull
request.

## TL;DR

- **Agent-authored PRs are welcome** — but only with a **named human sponsor** who
  has reviewed the diff and justifies it. See [Pull-request policy](#pull-request-policy).
- **Feature requests are welcome** — open an issue labeled `enhancement`. Describe
  the behavior and why, not the implementation.
- The one rule that outranks all others: **never report a result that was not
  actually observed.** Honesty is the product.

## What this project is

A stdio MCP server that controls and monitors LAN machines over SSH, scripted
RDP, `adb`, Wake-on-LAN, and local network probes. Its defining property is
honest, machine-checkable reporting: every capability gap, refusal, and partial
success is described with the evidence that was measured, never faked. See
[README.md](README.md).

## Pull-request policy

A pull request must satisfy **all** of the following or it will be closed without
review:

1. **Human sponsor.** The PR body names at least one human (a `@handle`) who has
   read the diff and takes responsibility for it. A PR that says "generated by
   <agent>" with no human is not reviewable and will be closed.
2. **Written justification.** The PR body explains:
   - *what* it fixes or adds, and *why* it matters;
   - *how* it was tested (commands run, tests added, results pasted);
   - what it does **not** claim — e.g. "the RDP path was not exercised live".
3. **Evidence, not assertion.** "It should work" is not evidence. Paste the actual
   `pnpm typecheck` and test output, or the tool result that demonstrates the fix.
4. **Focused diff.** One logical change per PR. No drive-by reformatting, no
   unrelated churn.
5. **Tests.** Behavior changes need test coverage; bug fixes need a regression
   test that fails before and passes after.

An agent may open the PR, comment, iterate, and respond to review — but the human
sponsor is accountable for correctness and safety. Maintainers may ask the sponsor
to confirm specific risky lines.

### Feature requests

Open an issue with the `enhancement` label. Good requests describe the operator
outcome ("I want host_status to also report the ssh cipher") rather than dictating
the code. Maintainers and agents alike may pick up labeled issues; the PR still
needs a human sponsor.

## The honesty contract (non-negotiable)

These invariants define "correct" here. A change that violates one is a bug no
matter how else it looks:

- **Never fabricate a success.** If an action did not happen or was not verified,
  the result must say so. Do not hard-code `truncated: false`, a signal you did
  not observe, a credential you did not resolve, or "available" you did not
  measure.
- **Report measured values only.** `exec` reports a signal only when the server
  confirmed one; a timeout says TERM was requested and the process *may* still be
  running; `admin_exec` says `not measured` when the probe is inconclusive.
- **Every refusal carries a hint.** New error paths must surface an actionable next
  step, in both the text line and `structuredContent` (fall back to `src/hints.ts`;
  override with a specific hint at the call site when you can).
- **Fail safe toward refusal** in the safety gate and the power/overwrite guards.

## Code invariants

- **Language/build:** TypeScript, Node ESM (`"type": "module"`, `Node16`
  resolution). Every relative import in `src/` must carry a `.js` extension. Node
  **≥ 20.6**.
- **Config schema:** every object schema is `.strict()`. Adding a field without a
  default and without validating it is a config-safety regression. Host names must
  remain uniquely resolvable.
- **Safety gate:** any new command-executing tool must route through
  `safety.checkCommand`. Do not weaken the self-sever patterns; if you change
  parsing, keep the refusal/over-refusal tests honest (both the refused set and the
  allowed set must still pass).
- **Secrets:** never commit a secret, private key, password, token, real host
  address, username, MAC, SID, or credential path. Tests use the RFC 5737
  documentation range (`192.0.2.0/24`) and clearly-fake fixtures. Secrets are
  resolved from the environment; nothing secret is echoed into tool results or
  logs.
- **No new required runtime deps** without justification in the PR. koffi FFI
  stays lazily loaded (importing a module must not touch FFI until first use).
- **Teardown:** preserve `registerTools()`'s dispose contract — monitors stop
  before the transport closes.

## Making a change

```bash
pnpm install
node node_modules/typescript/bin/tsc -p tsconfig.json              # build
node node_modules/typescript/bin/tsc --noEmit -p tsconfig.test.json # typecheck (src + test)
CONTROL_MCP_DISABLE_MAIN=1 node node_modules/vitest/vitest.mjs --run test/
```

Both typecheck projects must be clean and the whole test suite green. The
`CONTROL_MCP_DISABLE_MAIN=1` guard is required for tests because importing the
entry point otherwise starts the stdio server.

Prefer editing `src/` and keeping diffs reviewable; do not commit `build/`,
`node_modules/`, local config, or scratch files.

## What will not be accepted

- A PR that changes behavior to report a more optimistic outcome (that breaks the
  product's purpose).
- Unjustified or sweeping refactors, dependency bumps without a reason, or changes
  that loosen the safety gate / `.strict()` schema without a compelling argument.
- Anything containing live credentials or private network details.
